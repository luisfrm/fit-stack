## Payment Receipts (Panel + Console)

Panel receipts are internal payment records — never fiscal invoices (see `vaults/business/ORGANIZATION_RECEIPT_MODEL.md`). Source of truth for the frozen contract of the unified engine: the Linear document **"Receipt engine — frozen contract"** attached to the project Fit Stack, plus the Linear issues that document the model, the server-owned period with its compensation, and the unification chain.

- **Two-step emission**: step 1 **claims the payment first** (`receipt_claim_at`, single `UPDATE … WHERE receipt_claim_at IS NULL AND receipt_number IS NULL` that also persists the tax breakdown, the emitter snapshot and `issued_by`) and **only then** assigns the number atomically (single `INSERT … ON CONFLICT DO UPDATE … RETURNING`, per-org yearly sequence `{año}-n`, which no longer carries the organization slug), attaching it in a second statement (`WHERE receipt_number IS NULL AND receipt_claim_at IS NOT NULL`) — a concurrent emission loses the claim instead of racing for the sequence, so no correlative is burned; step 2 renders the PDF in `jobs-worker` (`fit-receipt-events` queue + DLQ, sweep cron 10 h pre-sale) and `PUT`s it to R2 (`receipts/<org>/<año>/<n>.pdf`, immutable, generated once).
- **Email only from step 2**, after `UPDATE … WHERE receipt_pdf_key IS NULL RETURNING` (`rowCount === 1` gate); `markReceiptNotified` with `clearReceiptNotified` rollback on send failure. The mark is **also cleared on the final failed delivery** (the one that dead-letters the message in `processTaskBatch`, detected with `isFinalDeliveryAttempt` + the shared `TASK_QUEUE_MAX_RETRIES`), so the sweep's second predicate recovers a payment whose email exhausted its retries instead of stranding a rendered PDF with no delivery. Accepted tradeoff: a deceptive final failure (e.g. timeout after the SMTP server already accepted) can produce one duplicate email via the sweep — losing a payment receipt is worse than receiving it twice.
- **Sweep covers five states** (`sweepPendingReceiptPdfs`, `jobs-worker`): *stale claim* (≥15 min and still `validated` — the emission claimed the row and died before numbering; resumed with a number, render enqueued, never renumbered: the local correlative is released only if it is still the last one. A claim left on a compensated/voided payment is terminal and never numbered), *numbered without PDF* (≥15 min — the render was lost), *PDF ready but unnotified* (≥30 min — the step-2 email never left), *voided without the sealed PDF* (≥15 min — the void was persisted but the ANULADO render never landed) **and** *voided without the flag* (≥15 min — the status change wrote `status = 'voided'` but `markVoided` was lost, so `receipt_voided = false`; every other predicate looks for the flag **SET**, so the row was invisible while the ORIGINAL PDF kept being served). The last one is repaired through `flagVoidedIfMissing` / `flagPlatformVoidedIfMissing`: a single statement that flips **only** the flag — `voided_by` / `voided_at` / `void_reason` are preserved verbatim, the sweep never invents an actor — and the sealed render is enqueued only when this run flipped it (`flagged: false` = another run won, nothing is queued twice). All five are safe to re-enqueue because each artifact has its own idempotent gate; a corrupt row never aborts the rest.
- **Explicit void outcome**: `markReceiptVoided` throws `RECEIPT_NOT_ISSUED` as an **internal service contract**, but `PATCH /api/payments/:id/status` (and its Console twin) answers **200** with `receiptVoided: boolean` + `receiptVoidReason: 'not_issued'` when there was no receipt to void — the status change is never reverted and the panel/console show a differentiated toast. Never text-match; the code is the contract.
- **ANULADO is an artifact, not just a flag**: voiding keeps the emission PDF **intact** (write-once) and materializes a **new** one with the seal (`<numero>-anulado.pdf`, `receipt_voided_pdf_key` column). The original **stops being delivered** as soon as `receipt_voided` is true: until the sealed PDF exists, the contract responds `pending` (202 + `/receipt/pdf` 404) — *fail-closed*: a voided receipt never travels without its seal. Voiding enqueues the render (step 1-bis) and the sweep's voided predicates are the backstop. It is not re-sent by email either: **409 `RECEIPT_VOIDED`** (the email would go out with the unsealed PDF), although an event already in flight is also discarded in the handler.
- **Contract**: `GET /:id/receipt` → 200 ready / 202 pending / 200 `available:false,reason:pre_system` (never 409); `GET /:id/receipt/pdf` binary download; `POST /:id/issue` manual fallback (owner/manager/cashier).
- **Validated ⇔ numbered invariant**: issuance is decided by the **persisted** state (`createdPayment.status`), never by the payload — `payment.status` is optional in the contract and the repo normalizes it to `validated`, so deciding by the payload left a validated payment **without** a number, without render and without email (and the PATCH to `validated` does not repair it: `wasPending` is already false; only `POST /:id/issue` does). Since RD-155 the gym `PATCH /api/payments/:id/status` no longer *produces* that state: a failed emission compensates the approved charge to `voided` (audit, no number, subscription untouched) and re-throws the original error, while the route invalidates the 7 cache keys in `finally`.
- **Document gate** forces `"Comprobante de pago"` (`HAS_FISCAL_HOMOLOGATION=false` by construction); the technical UUID is never shown (only `receiptNumber`); voided = `ANULADO`, the number is never released or reused; serial audit at `GET /api/reports/receipts` (rows + per-currency totals + `gaps[]` = `1..lastNumber` per org/year).
- **Fiscal gating (fail-closed)**: `COUNTRIES` is the tax **SSOT** (rates + conditions) and `isFormalTaxpayer` is the only fiscal switch, written **only from Console** (`PATCH /api/platform/organizations/:id`). The tenant route edits `legalName`/`taxId`/`address`/`disclaimerOverride` and answers **403 `FISCAL_CONFIG_PLATFORM_ONLY`** (with `fields`) for `isFormalTaxpayer`, the legacy `taxes`/`confirmedTaxes` or a `null` reset, with no partial write. Console activation requires a complete issuer identity (`legalName` + `taxId` + `address`), otherwise **400 `FISCAL_IDENTITY_INCOMPLETE`** (no partial write). While `isFormalTaxpayer` is falsy the receipt **never details taxes**: `subtotal = amountPaid`, `taxTotal = 0`, `taxDetails = []`; when truthy every `countryTaxes` / `conditionalTaxes` entry applies as the country defines it, with the condition evaluated at calculation time (VE IGTF 3% only when `payment_currency !== 'VES'`, `basis: 'gross_first'` = extracted from the gross total before the IVA base). The breakdown is **always computed server-side** with `computeInclusiveTaxes` (same function as the panel preview): there is **no manual override** — no UI, no payment-write fields, no `applyTaxOverride`, and `payment.tax_override_reason` is legacy read-only for historical rows. Panel `settings/organization` shows the regime read-only and lets the tenant edit only the disclaimer. The platform emitter (FitStack) is **not** declared formal, so SaaS `FS-N` receipts carry no breakdown (see RD-138 — dynamic country taxes — and RD-145 — fiscal config restricted to Console — in Linear, project «Fit Stack»).
- **Document fidelity**: the PDF/contract **omit** lines without data (tax id, address, recipient document, recipient address) — never filled with placeholders (`---`); `checklistPrePdf` rejects a visible placeholder (omitting is the correct path). The UUID scan inside that checklist covers **system-generated fields only** (document number/label, emitter, recipient, plan and method names): the operator's free-text details (`method.maskedDetails`) are deliberately **not** scanned, because judging operator input is write-side validation's job (`paymentMethodSchema`) — a bank reference shaped like a UUID must not strand the receipt without a PDF or an email. Do not re-add it. If `currencyPaid ≠ baseCurrency` it prints `1 {base} = {rate} {paid}` **plus** the base-currency equivalent (`amounts.baseTotal`), which is the **persisted base amount** — the frozen `plan_snapshot_price` (Panel) / `base_amount` (Console) — never a division (RD-157). Dividing the paid amount by the stored rate survives only as the documented fallback for historical rows without that base amount, and rounds money: `numeric(10,4)` turned `0.00025` COP→USD into `0.0003` (~20% error), so both `exchange_rate_applied` columns are now `numeric(20,10)` (migration `0027`, additive, no backfill).
- **Emitter snapshot**: step 1 persists `emitterSnapshot` (jsonb) **in the claim statement, before the number is consumed** — the claim writes `subtotal` / `tax_total` / `tax_details` / `emitter_snapshot` / `issued_by`, and the attach writes only the number, `receipt_issued_at` and `document_type`. The snapshot carries `version`, frozen `emitter` (name/legalName/taxId/taxLabel/address/countryCode/currency), the label applied by the gate, the label of the recipient document, the `disclaimer`, the `timezone` used to print dates and the resolved fiscal profile (`taxes[]` = name/rate/enabled). `recipientDocLabel` holds the label the document actually prints for the recipient: `taxLabel` (`R.I.F.`, `NIT`) when the recipient is an organization (Console/SaaS) and `docLabel` (`C.I.`, `C.C.`) for an individual (Panel member). Snapshots issued before that distinction keep their persisted `docLabel` and render as-is — the frozen snapshot is never re-labelled (terminal, documented state) and `assertEmitterSnapshot` requires nothing new. The compose reads the snapshot **first and skips live config entirely** (`resolveFiscalProfile` is not even evaluated), so `GET /:id/receipt` is reproducible after the emitter edits its profile. `NULL` = emitted before the snapshot existed (migration `0016`) → composed live (terminal, documented state); a present-but-invalid snapshot **throws** (never silently degrades).
- **Emission traceability**: `issuedBy` (actor of the numbering request) travels from the session (`c.get('user')?.id`) through `subscriptions.service` / `payments.route` / `platform-subscriptions.*` into `claim*Receipt` (persisted with the claim, not with the number). Step 2 never writes it; the claim sweep resumes a stale claim with `issued_by = NULL` (the original actor is unknown) and never overwrites an existing value: an existing `issued_by` is never overwritten or invented (`NULL` = historical, automatic or resumed emission). Both reports expose `issuedBy` + `emitterName` (from the snapshot) and the CSV export includes them.
- **Core + profiles, not mirrored code**: the sequence lives **once per step** and every issuer contributes a tiny profile — step 1 `apps/api-worker/src/services/receipt-issue.core.ts` (`issueReceipt` + the `IssuerProfile` port; `receipts.service.ts` / `platform-receipts.service.ts` keep only the profile plus the `state`/`void`/`email` methods, factory signatures intact), step 2 `apps/jobs-worker/src/handlers/render-profile.ts` (`renderReceipt` + `createPanelRenderProfile` / `createPlatformRenderProfile`; `receipt.handler.ts` only selects the profile by `event.scope` and keeps the sweep), and the `payment → ReceiptData` mapping `packages/shared/src/documents/receipt-composer.ts` (`composePanelReceipt` / `composePlatformReceipt` over structural row types — never imports `@workspace/database`); `receipt-compose.ts` keeps `assembleReceiptData` as the single assembly block and the previous builders as internal mappers. `pdf.handler.ts` resolves the email attachment through one shared resolver in both branches. The R2 key year stays per issuer on purpose (Panel: local year of the persisted number; Console: UTC year of `receiptIssuedAt`) — business, not duplication.
- Shared-repo exception ([§1 Monorepo Boundaries](../../AGENTS.md#1-monorepo-architecture--boundaries)): `packages/database/src/repositories/receipts.repository.ts` + `platform-receipts.repository.ts` — the only shared repos (two runtimes need identical SQL each). Unifying the two twins behind a table adapter is a **frozen discarded decision** (shapes sketched and rejected, with reasons, in [`technical-standards.md` §1](../architecture/technical-standards.md): the typed table bag loses `SET` key/value checking, the discriminated union makes the shared module know both issuers; re-open only if the payment tables converge or Drizzle ships typed table-generic builders).

> Columns (emitter snapshot + issued_by): `payment.emitter_snapshot` / `payment.issued_by` and their twins on `platform_subscription_payment` — migration `0016`, additive nullable, no backfill (`NULL` = pre-snapshot emission).

> Columns (ANULADO PDF + duration snapshot): `receipt_voided_pdf_key` on `payment` and `platform_subscription_payment` + `idx_payment_voided_pending` / `idx_psp_voided_pending` (partial indexes of the 3rd predicate) and the gym `payment.plan_snapshot_duration_value` / `plan_snapshot_duration_unit` — migration `0018`, additive nullable, no backfill (`NULL` = voided before the ANULADO PDF artifact → the sweep recovers it; duration without snapshot → the calculation falls back to the live plan).

> Column (claim-first emission, RD-140): `receipt_claim_at` (`timestamptz`, nullable) on `payment` and `platform_subscription_payment` + `idx_payment_receipt_claim_pending` / `idx_psp_receipt_claim_pending` (`(receipt_claim_at) WHERE receipt_claim_at IS NOT NULL AND receipt_number IS NULL`, the stale-claim predicate) — migration `0026`, additive nullable, no backfill (`NULL` = numbered before the claim existed). The claim is the concurrency gate: it is never released, only resumed by the sweep. Applied by CI (`database-migrations.yml`) on merge.

> Column type (exact rates, RD-157): `exchange_rate_applied` on `payment` and `platform_subscription_payment` goes from `numeric(10,4)` to `numeric(20,10)` — migration `0027`, additive type widening, no backfill and no rewrite of historical values (`0.0003` stays `0.0003`). Applied by CI (`database-migrations.yml`) on merge.

> Payment-status migration (`0017`, additive/backward-compatible): sets `platform_subscription_payment.status` default to `'processing'` and normalizes legacy data (`pending → processing`, `invalid → voided`, marking `receipt_voided`/`voided_at`/`void_reason` when a receipt existed). Applied by CI (`database-migrations.yml`) on merge. After merge, no row may carry `pending`/`invalid`.

> Column `0019` (additive nullable, no backfill): `subscription.end_date_override_reason` (motivo exigido al acortar un periodo vigente, `NULL` en el resto de casos). Pendiente de aplicar — se aplica por CI (`database-migrations.yml`) al hacer merge; no correr `db:migrate` manual. Solo añade una columna: el conteo de tablas sigue en **33**.

**Console (SaaS) receipts** mirror the same guarantees with one legal emitter (FitStack):
- Global continuous sequence `FS-N` (no year reset) + same two steps on the same `fit-receipt-events` queue (`scope:'platform'`); R2 keys `platform/receipts/<año-UTC>/FS-<n>.pdf`; sweep covers both tables.
- Same 3-state contract at `GET /api/platform/subscriptions/payments/:id/receipt` (+ `/receipt/pdf` binary, `POST /resend` with the 4 frozen branches); reads allow `subscription:list` (support downloads), writes require `console:manage` (support 403).
- Trial/free $0 never burn the series (`available:false,reason:pre_system`); payer persisted only at `processing` creation, validation never overwrites; year/period in UTC (platform billing convention).
- Voided SaaS payments keep number + PDF and set the ANULADO flag (`markPlatformReceiptVoided` on status →VOIDED, fixed reason, `by` required fail-closed); without a number the service code is `RECEIPT_NOT_ISSUED` but the endpoint answers **200** with `receiptVoided: false` + `receiptVoidReason: 'not_issued'`; voiding never cancels the subscription nor reverts the cumulative period; `refunded` (reserved, no flow produces it) doesn't touch the flag and `voided` is the only annulment state (`rejected`/`annulled` is derived with `getVoidKind`). Same rule as the Panel: the ANULADO PDF is a separate artifact (`platform/receipts/<año-UTC>/FS-<n>-anulado.pdf`), the emission PDF stops being delivered while it is missing and `POST /resend` answers **409 `RECEIPT_VOIDED`**.
- Emitter identity in `platform_setting` (`fitstack_*`, console Settings → Emitter); empty = generic "FitStack" + gate Payment receipt.
- **Emitter fiscal wording (RD-160)**: the `taxLabel` and the `disclaimer` of an `FS-N` come from the **issuer's** country (`fitstack_country_code`), never from the recipient's: a VE-configured FitStack billing a CO organization prints `R.I.F.` + the SENIAT disclaimer for itself and `NIT` for the recipient. With no `fitstack_country_code` the issuer is generic (`taxLabel: 'Tax ID'`, printed only when `fitstack_tax_id` exists, and `['Comprobante de pago interno. No constituye una factura fiscal.', 'Emitido por FitStack']`) — the recipient's country is never used as a proxy for the fiscal wording. `buildPlatformEmitterSnapshot` receives both profiles (issuer for wording, recipient for `recipientDocLabel` and the tax summary, always disabled); an unknown issuer country fails visibly (`500 FISCAL_PROFILE_UNKNOWN` at issuance). The frozen snapshot keeps the rule reproducible (`isFormalTaxpayer`/`HAS_FISCAL_HOMOLOGATION` untouched: still "Comprobante de pago").
- **B2B recipient wording (RD-150)**: the receptor of an `FS-N` is an **organization**, so the recipient block prints the country `taxLabel` (`R.I.F.` in VE, `NIT` in CO) — never the person-natural `docLabel` — and never the "Socio / Cliente" / "… DEL SOCIO" wording used by the Panel. The distinction is **structural** (`ReceiptRecipient.kind = 'organization'`, set by `composePlatformReceipt`), never a text heuristic, so the Panel (gym → member) keeps `docLabel` + its labels untouched. The recipient's fiscal address (`organization.address`) is printed when registered and **omitted when absent** (no placeholder); the field travels as an optional `ReceiptRecipient.address` (RD-106 will populate the member address through the same line).
- **Audit parity**: the audit of the global series lives at `GET /api/platform/subscriptions/receipts` + `/subscriptions/receipts` (console page with URL filters + CSV export up to 1000 rows), mirroring the Panel. Same `computeReceiptGaps` algorithm with an **injected strategy** (Panel: `{año}-{seq}` annual; Console: `FS-{seq}` continuous, no year) → `gaps[]` classifies `hueco` vs `anulado` identically on both sides. Console filters run in **UTC** (platform billing convention); `year` there means the UTC year of `payment_date`, not a sequence universe. `support` reads (200); writes stay 403.
